# 企业 AI 项目交付方法

## 交付主线

企业 AI 项目不能以“Demo 能运行”作为结束。本参考方法使用一条可追踪的交付链，将每个阶段的输入、决策和验收证据连接起来。

```text
现状调研
  → 云与 AI 成熟度评估
  → 目标架构与范围确认
  → 部署实施与运行手册
  → 功能、性能与安全测试
  → 验收与运营交接
```

## 1. 现状调研

先确认问题是否适合使用 AI，而不是从模型开始倒推需求。

主要工作包括：

- 访谈业务、技术、安全和运维角色；
- 梳理现有流程、数据来源、系统接口和责任边界；
- 收集高频场景、失败案例和人工处理方式；
- 识别数据质量、权限、时效性和合规风险；
- 形成现状问题、业务目标和候选用例清单。

阶段出口：相关方认可问题定义、优先级和成功指标。

## 2. 成熟度与可行性评估

评估组织是否具备把 PoC 变成可运营系统的条件。

| 评估维度 | 关键问题 |
|---|---|
| 数据与知识 | 数据是否可用、可授权、可更新、可追踪？ |
| 基础设施 | 模型、存储、网络和 GPU 是否满足目标负载？ |
| 系统集成 | 是否有稳定 API、身份体系和状态回写机制？ |
| 安全与治理 | 谁能访问、谁能批准、如何审计和回滚？ |
| 团队与运营 | 谁维护知识、工作流、模型和线上问题？ |

阶段出口：确定“本阶段完成什么、明确不做什么、以后如何演进”。

## 3. 目标架构与范围设计

将需求转换为可实施的系统边界和技术方案。

- 定义业务应用、业务控制、AI 编排和模型服务的职责；
- 设计数据流、状态流、人工确认点和异常路径；
- 确定 RAG、模型、工作流、数据库和对象存储方案；
- 明确接口、认证、权限、日志、监控和容量要求；
- 为每项能力建立功能验收和非功能验收标准；
- 输出目标架构、模块设计、接口边界和阶段路线图。

阶段出口：架构能解释业务流程，也能解释安全、稳定性和维护方式。

## 4. 实施与部署

部署文档不是最后补写的附件，而是架构可落地性的验证。

- 固定运行环境、镜像、模型、依赖和配置版本；
- 按模型服务、智能引擎和业务应用分别部署；
- 提供健康检查、接口验证和最小回滚路径；
- 验证知识导入、工作流调用、业务状态写回和文件链路；
- 记录已知限制、故障处理和日常维护方法。

阶段出口：另一名工程师可以依据运行手册完成部署和基础验证。

## 5. 测试与验收

测试同时覆盖功能、质量、性能和安全，而不是只看生成结果。

| 类型 | 代表性验证 |
|---|---|
| 功能 | 正常流程、权限、状态流转、知识更新和人工接管 |
| AI 质量 | 解析、分类、检索、引用、答案和建议的抽样评测 |
| 性能 | 单请求延迟、并发、长稳、队列、GPU 与资源利用率 |
| 安全 | 输入、上传、鉴权、越权、重放、信息泄露和依赖风险 |
| 运维 | 指标、日志、告警、故障定位、重试、回滚和数据恢复 |

测试结果必须能关联到需求和验收条目。本作品集只展示通用方法，不包含任何实际项目的测试数据、拓扑或阈值。

阶段出口：所有关键条目有结果、有证据、有责任人；遗留问题有接受或整改结论。

## 6. 运营交接

- 明确业务、知识、模型、工作流、平台和安全责任人；
- 建立知识过期、低质量回答和失败任务的处理队列；
- 设置模型、Prompt、工作流和配置的变更流程；
- 定期复盘业务指标、AI 质量、系统性能和用户反馈；
- 根据观测到的负载决定是否扩容或升级推理架构。

## 交付物之间的关系

| 交付物 | 回答的问题 |
|---|---|
| 现状调研 | 为什么需要建设，当前问题在哪里？ |
| 成熟度评估 | 现有条件是否支持，缺口是什么？ |
| 目标架构 | 应该怎样建设，系统边界是什么？ |
| 部署运行手册 | 如何部署、验证、维护和恢复？ |
| 测试报告 | 功能、性能和安全是否达到约定？ |
| 验收记录 | 是否可以交接，遗留风险由谁承担？ |

## 项目负责人的重点

- 把模糊需求转换为场景、流程、边界和验收指标；
- 让业务、AI、开发、基础设施、安全和运维使用同一套范围定义；
- 在效果、成本、风险、周期和团队能力之间做可解释的取舍；
- 及时区分本阶段范围与未来目标架构，避免过度承诺；
- 确保项目结束时不仅有系统，也有文档、测试证据和运营责任。
